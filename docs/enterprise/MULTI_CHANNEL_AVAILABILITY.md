# Enterprise Multi-Channel Availability

FitOra remains the system of record for capacity. `CourtSlot.operationalState` stores only owner
overrides; `HELD` and `BOOKED` are derived from `reservedCount`, `confirmedCount`, and bookings.
Every availability response includes `lifecycleStatus` while retaining the legacy fields.

## Channel authentication

Channel APIs use `x-fitora-api-key`. Keys are generated when a manager creates an integration,
stored as SHA-256 hashes, and returned in plaintext once. Provider credentials and webhook secrets
are encrypted with AES-256-GCM using `INTEGRATION_ENCRYPTION_KEY`.

- `GET /api/v1/availability?venueId=<uuid>&date=YYYY-MM-DD`
- `POST /api/v1/slots/hold` (five-minute hold)
- `POST /api/v1/slots/release`
- `POST /api/v1/bookings`
- `POST /api/v1/bookings/cancel`

`POST /bookings` selects API-key authentication when `x-fitora-api-key` is present and otherwise
preserves the existing JWT player flow. Channel create/hold requests require a stable
`idempotencyKey`; booking creation also requires `externalBookingId`.

## Normalized webhook contract

Proprietary Playo and PlayArena contracts are not assumed. Providers must be translated at the
edge to this versioned FitOra shape:

```json
{
  "eventId": "provider-event-123",
  "type": "booking.created",
  "occurredAt": "2026-07-21T10:00:00.000Z",
  "data": {
    "courtId": "uuid",
    "slotId": "uuid",
    "externalBookingId": "vendor-booking-42",
    "idempotencyKey": "vendor-operation-42",
    "seats": 1
  }
}
```

Supported types are `booking.created`, `booking.cancelled`, `slot.hold`, and `slot.release`.
Send the raw JSON to `POST /api/v1/integrations/:provider/webhook` with:

- `x-fitora-integration-id`: connection UUID
- `x-fitora-signature`: lowercase HMAC-SHA256 hex digest of the raw request body

Event IDs are unique per integration and duplicate deliveries return success without reprocessing.

## Outbound synchronization

Managers configure an HTTPS `outboundEndpoint`; no undocumented vendor endpoint is embedded.
FitOra posts normalized availability snapshots with a ten-second timeout,
`x-fitora-idempotency-key`, and `x-fitora-signature`. Lifecycle transactions insert durable
`integration_sync_jobs`; BullMQ only accelerates processing. Failed jobs use exponential backoff,
become dead-letter records after eight attempts, and can be retried or regenerated by manager APIs.

Manager routes under `/api/v1/integrations` provide connection CRUD, slot mappings, health,
failed syncs, retries, conflicts, manual resync, and aggregate monitoring stats.

## Provider limitations

Playo and PlayArena adapters intentionally use the normalized contract and configurable endpoint.
Production activation still requires each provider's approved URL, authentication fields, event
mapping, signing requirements, rate limits, and certification test vectors. Store those credentials
in the encrypted connection payload; do not log them.
