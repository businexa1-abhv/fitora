FitOra — Application Architecture

Multi-sided sports & fitness platform · Turborepo monorepo · Version 1.0 · July 2026

1. Architecture Style

FitOra uses a modular monolith today — a single NestJS API with clear domain-module boundaries — designed to extract into domain-oriented microservices when scale demands it.

API-firstAll clients (web, admin, mobile) share one versioned REST API at /api/v1
Modular monolithNestJS domain modules with clear ownership; extract only when justified by scale
Pay-before-confirmPayment completion drives all state transitions via a unified PaymentsService
Role-aware by designRBAC enforced at API layer; clients adapt UI by role
Fail closedAuth and permission checks default to deny; public routes are explicit opt-outs
Cache-asideRedis accelerates reads; PostgreSQL remains source of truth
Shared contractsTypes, enums, constants in @fitora/shared — single source of truth
Observable by defaultStructured logs, health checks, error tracking from day one

Web Architecture Pattern

Client-heavy SPA with 'use client' for interactive flows; SSR/static for SEO pages. No Next.js API routes for business logic — all data flows through NestJS for consistency across all clients.

Mobile Architecture Pattern

Expo Router (file-based routing), SecureStore for refresh tokens, Firebase FCM for push notifications, deep linking for booking confirmations and order updates.

7. Payments — Polymorphic Architecture

All monetizable entities share a single PaymentsService. Entity type determines the post-payment action.

Entity TypeAction on PAID
BOOKINGStatus → CONFIRMED, generate check-in code
MEMBERSHIPActivate, set start/end dates
TRAININGEnrollment → ACTIVE, set enrolledAt
SHOP_ORDERConfirm order, decrement stock, clear cart
MARKETPLACE_ORDERStatus → ACCEPTED

Payment State Machine

PENDING
→ verify / webhook →
PAID
→ refund →
REFUNDED
PENDING
→ failure / timeout →
FAILED

Razorpay HMAC SHA256 signature validation · Idempotency on webhook re-delivery · PAYMENT_MODE=mock for local dev.
